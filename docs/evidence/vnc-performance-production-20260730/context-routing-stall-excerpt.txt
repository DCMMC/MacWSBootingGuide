Runtime evidence for the redundant post-secondary target probe
===============================================================

Before the OSXvnc routing change, macwsinputd accepted the authoritative
SecondaryTap for Terminal and then immediately waited on a second target
probe. Terminal's main thread was already inside the real synchronous menu
tracker, so the query received no reply:

MACWS-INPUT TARGET-REPLY nonce=1 pid=32651 window=18 flags=0xf
MACWS-INPUT TARGET-PROBE nonce=1 endpoints=1 sent=1 replies=1 selected=32651 window=18 score=7 selected-active=YES selected-front=YES competing-active=NO incomplete=NO ambiguous=NO system-menu=NO
MACWS-INPUT ACTIVATE seq=3 kind=activate-target target=32651 window=18 repair=NO menu-preflight=NO deactivated=0 sent=SKIPPED errno=0
MACWS-INPUT TARGET-REPLY nonce=2 pid=32651 window=18 flags=0xf
MACWS-INPUT TARGET-PROBE nonce=2 endpoints=1 sent=1 replies=1 selected=32651 window=18 score=7 selected-active=YES selected-front=YES competing-active=NO incomplete=NO ambiguous=NO system-menu=NO
MACWS-INPUT HOVER-OWNER seq=4 pid=32651 window=18 frame=(1000.00,800.00)/2388x1668 quartz=(500.00,400.00)
MACWS-INPUT RX seq=5 scene=564e430000000001 kind=secondary-tap target=0 frame=(1000.00,800.00)/2388x1668 quartz=(500.00,400.00) event=3 created=NO post=issued route_errno=0 cursor=unavailable(-1.00,-1.00) samples=0 capture=0
MACWS-INPUT ROUTE seq=5 route=appkit-socket pid=32651 window=18
MACWS-INPUT TARGET-PROBE nonce=3 endpoints=1 sent=1 replies=0 selected=0 window=0 score=-1 selected-active=NO selected-front=NO competing-active=NO incomplete=NO ambiguous=NO system-menu=NO
MACWS-INPUT HOVER-OWNER seq=6 pid=0 window=0 frame=(1000.00,800.00)/2388x1668 quartz=(500.00,400.00)

ProbeAppInputTarget has a source-level 150,000,000-ns deadline. The zero-reply
probe therefore serialized later hover and Escape records behind a query whose
answer was already present in menuTarget.

After the change, the same sequence contains only the authoritative activation
probe and SecondaryTap. There is no post-tap TARGET-PROBE and the Escape pair
can be routed immediately:

MACWS-INPUT TARGET-REPLY nonce=4 pid=32651 window=18 flags=0xf
MACWS-INPUT TARGET-PROBE nonce=4 endpoints=1 sent=1 replies=1 selected=32651 window=18 score=7 selected-active=YES selected-front=YES competing-active=NO incomplete=NO ambiguous=NO system-menu=NO
MACWS-INPUT ACTIVATE seq=12 kind=activate-target target=32651 window=18 repair=NO menu-preflight=NO deactivated=0 sent=SKIPPED errno=0
MACWS-INPUT RX seq=13 scene=564e430000000001 kind=secondary-tap target=0 frame=(1000.00,800.00)/2388x1668 quartz=(500.00,400.00) event=3 created=NO post=issued route_errno=0 cursor=unavailable(-1.00,-1.00) samples=0 capture=0
MACWS-INPUT ROUTE seq=13 route=appkit-socket pid=32651 window=18
MACWS-INPUT KEY seq=15 kind=key-down target=32651 keycode=53 keysym=0xff1b modifiers=0x100 sent=YES errno=0
MACWS-INPUT KEY seq=16 kind=key-up target=32651 keycode=53 keysym=0xff1b modifiers=0x100 sent=YES errno=0

The event was not replaced or synthesized by this change. ActivateTarget still
selects menuTarget, and the existing atomic SecondaryTap remains the sole
right-click owner. Only the duplicate query after the known secondary gesture
was removed.
