Device: iPad13,6, iOS 16.3.1; macOS 13.4 chroot; native AGX path
Mode: macos_gui.sh start coexist --experimental --no-terminal
Application: GlassDemo
Source base: cd27d08 plus the input/dirty-rectangle changes described here

This record separates a proved stationary-click fix from the still-incomplete
drag and frame-rate work.  The command-ABI and cancelled-swap switches enabled
by --experimental remain diagnostic scaffolding; process uptime is not used as
a rendering witness.

1. Runtime-confirmed lost transition before the change
-------------------------------------------------------

The pre-change VNC hook created a new nonblocking datagram socket for every
pointer record.  Device logs contained a mouse-down send failure followed by a
successful mouse-up.  AppKit therefore received an incomplete gesture.  The
original OSXvnc CGEvent path is not a fallback in this launchd session because
CGPreflightPostEventAccess returned NO at runtime.

The replacement keeps one sender socket, bounds continuous motion to 120 Hz,
and gives button transitions eight bounded nonblocking retries.  A stationary
primary click is held inside OSXvnc until release and sent as one version-3,
52-byte MacWSInputKindTap record.  The target-process bridge constructs the
matching AppKit down/up pair locally, queues up before synchronously dispatching
down, and never substitutes a direct control action.

3. Ordered queue and bounded backpressure
-----------------------------------------

The per-application bridge now owns every queued NSData explicitly (the socket
thread has no autorelease pool), coalesces adjacent move/hover samples for one
gesture, and caps continuous backlog at 128 while never evicting a button
transition.  macwsinputd uses one attempt for disposable motion and eight for
down/up/cancel/tap.  A PF550 deep capture is armed only on gesture completion;
the previous per-motion arming amplified a drag into repeated full-frame GPU
captures.

The VNC framebuffer hook also copies only the clamped rectangle requested by
OSXvnc rather than copying all 15,932,736 Retina pixel bytes for every dirty
rectangle callback.  The initial/full request remains a full copy.

4. Drag boundary remains open
------------------------------

The first drag test used coordinates read from a scaled preview rather than
the RFB's physical coordinate space and is not a control witness.  A second
test used the physical slider-knob point (820,766) and released at (1120,766).
Transport and the target-process run loop completed in order:

  #### OSXVNC INPUT kind=1 gesture=2 point=(820.0,766.0)/2388x1668 sent=52 errno=0 attempts=1 reliable=YES
  #### OSXVNC INPUT kind=3 gesture=2 point=(1120.0,766.0)/2388x1668 sent=52 errno=0 attempts=1 reliable=YES
  #### APP-INPUT DEFER pid=73775 kind=1 window=4
  #### APP-INPUT DRAG-COMPLETE pid=73775 gesture=2 window=4 first-move=(450.00,451.00)
  #### APP-INPUT POST pid=73775 kind=3 window=4 screen=(560.00,451.00) local=(463.00,391.00)

`DRAG-COMPLETE` was the exact diagnostic string in that deployed build; because
it only meant that `sendEvent:` returned, the source immediately renamed it to
`DRAG-DISPATCH-RETURN` to avoid promoting dispatch return to control success.
Furthermore, a byte-for-byte PNG comparison found zero changed pixels in the
slider ROI.  A stationary tap at the release point also produced no slider-ROI
change.  The only later changes were in animated content.  Therefore the
current evidence proves transport/order but NOT NSSlider tracking semantics.
The next diagnostic must log the actual AppKit hit view / NSSlider mouseDown
entry and must not replace the control action with a synthetic setter.

5. Startup and safety observation
---------------------------------

launchd status -10 during AGX initialization.  No new CrashReporter file was
created.  The existing watchdog requested one restart; PID 73840 then produced
a validated 2388x1668 frame and stayed alive for the interaction test.  This is
recorded as an unresolved startup instability, not hidden as a successful first
