# Native-AGX persistent-VNC multi-application input soak (2026-07-28)

## Scope

This milestone follows the persistent framebuffer-generation fix.  It tests a
different invariant: an untargeted RFB click must still reach the visible
AppKit application when Terminal and GlassDemo are alive at the same time.
The test uses OSXvnc directly; MacWS Host is not the pixel or input transport.

Device: iPad13,6, iOS 16.3.1, macOS 13.4 chroot.  Desktop negotiated by the
same RFB connection for the full soak: 2388x1668.

## Runtime-confirmed failure before the change

OSXvnc successfully sent the 52-byte tap record:

    #### OSXVNC INPUT kind=6 gesture=1 point=(512.0,562.0)/2388x1668 sent=52 errno=0 attempts=1 reliable=YES

Both AppKit applications had healthy per-process sockets, but the broker's
CoreGraphics query returned no list in its launchd session.  Because two
endpoints existed, the previous sole-endpoint fallback correctly refused to
guess and the real application bridge received nothing:

    MACWS-INPUT TARGET-LIST point=(256.00,281.00) result=NULL
    MACWS-INPUT RX seq=1 scene=564e430000000001 kind=tap target=0 frame=(512.00,562.00)/2388x1668 quartz=(256.00,281.00) event=1 created=YES post=issued route_errno=39 cursor=observed(256.00,281.00) samples=1 capture=1785168865820119000
    MACWS-INPUT ROUTE seq=1 route=global-fallback pid=0 window=0

This is runtime confirmation of the routing failure.  It is not attributed to
AGX or to an RFB socket failure: the first hop reported a complete send, while
the target-process logs had only `APP-INPUT READY/THREAD` and no `RX`.

## Upstream target-resolution protocol

`macwsinputd` now sends a versioned, nonce-bound hit-test probe to every live
`macws_app_input.<pid>.sock`.  The application handles that probe on its main
thread, reads `orderedWindows`, `isVisible`, `isActive`, and `keyWindow`, and
returns only metadata.  A probe never constructs or posts an NSEvent.

The broker ranks only replies whose local visible window contains the point.
An active application outranks an inactive one, then a key window breaks the
remaining tie.  Equal-ranked overlapping replies remain unresolved.  The
original 52-byte event is sent to exactly one selected PID; it is never
broadcast.  If a reply misses the deadline, a non-active result cannot steal
the click from a potentially blocked foreground app.

The new wire structs have compile-time sizes:

    MacWSInputTargetProbe = 32 bytes
    MacWSInputTargetReply = 28 bytes

Stale reply datagrams are drained before each nonce.  Cleanup removes the new
`/private/tmp/macws_input_target.sock` on normal stop and WS recovery.

With Terminal PID 15641 behind GlassDemo PID 15694, both endpoints replied.
Terminal reported no local hit.  GlassDemo reported hit + active + key
(`flags=0x7`), and only GlassDemo received the actual input record:

    MACWS-INPUT TARGET-REPLY nonce=2 pid=15641 window=0 flags=0

The application-side target reply also measured the actual AppKit window:

    #### APP-INPUT TARGET-REPLY pid=15694 nonce=2 window=11 flags=0x7 frame=(97.0,60.0 1000.0x728.0) sent=28 errno=0

This corrected a diagnostic false lead during the run.  A local image viewer
had resized the 2388-pixel PNG to 2048 pixels for display; coordinates read
from that preview were incorrectly reused as raw RFB coordinates.  The real
AppKit frame is consistent with the Retina desktop: its 2x pixel bounds are
x=194..2194 and y=92..1548.  The successful raw RFB point `(640,703)` maps to
the exact AppKit hit point `(320,482.5)` logged above.  There is no evidence of
a display/input scale mismatch in this run.

`misc/vnc_interactive_soak.py` retained one RFB connection and one accumulated
framebuffer for all iterations.  Every click kept an incremental request
outstanding and required a changed full-resolution raw rectangle; reconnecting
could not manufacture a pass.

## Build, boundaries, and cleanup

Because this changed both `macwsinputd` and `libmachook`, the first deployment
used a full Theos package/install/postinst cycle.  The installed macwsinputd
CDHash reported by postinst was:

    21a2fbc991f4168d7c7d6697b90447e6671ffd21

A later frame-only diagnostic log addition used the true libmachook-only
`--fast-force` path.  Both builds compiled the new code and completed signing,
trustcache registration, and rootfs deployment.

The soak used `--no-watchdog` only because the normal experimental watchdog
has an intentional 300-second total diagnostic cap.  CPU, RSS, PID, and error
counts were sampled manually during the bounded run.

The first post-soak safety check caught a recovery gap: the already-running
iOS `MacWSHost` UIKit process survived procursus `pkill` and reloaded
WindowServer after cleanup. `misc/cleanup_all.sh` now removes its exact dynamic
`UIKitApplication:com.macwsguide.host[...]` launchd label and, if necessary,
kills only the `Applications/MacWSHost.app/MacWSHost` executable path. A fresh
cleanup followed by an eight-second delayed check reported mode flag absent,
no GUI processes, no launchd jobs, and VNC stopped. This is the final cleanup
witness for the milestone.

This closes persistent VNC input targeting with two simultaneously live AppKit
applications for tap/NSButton semantics.  It does not claim keyboard, scroll,
right-click, arbitrary modal-loop targeting, drag, or long thermal stability.
