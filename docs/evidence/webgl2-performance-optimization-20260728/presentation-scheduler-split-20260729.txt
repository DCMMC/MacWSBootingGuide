VS Code WebGL2 presentation-scheduler split — 2026-07-29
========================================================

Question
--------

After the private IOGPU event selector fix, is the remaining iPad/M1 gap in
ANGLE command generation / native AGX execution, or in the visible-frame
requestAnimationFrame/presentation path?


Controlled configuration
------------------------

Both systems ran the official VS Code 1.130.0 application with Electron 42.6.0
and Chromium 148.0.7778.280. Both used ANGLE Metal, a 512x512 WebGL2 canvas,
1,000 scissored draw calls per batch, a fresh shader nonce, and
EXT_disjoint_timer_query_webgl2. The same benchmark source was used without a
device-specific branch.

Two producers were compared:

* `driver=raf`: one batch per requestAnimationFrame callback, measuring the
  real visible-frame scheduling path.
* `driver=timeout`: one batch per setTimeout(0), deliberately removing rAF and
  presentation permission from producer cadence while preserving the same
  WebGL commands, gl.flush, GPU query, and result collection.

The iPad WindowServer ran headless coexistence mode with VNC, Terminal and the
watchdog disabled. `/private/tmp/macws_coexist_pace_us` contained 16667. The
device was unlocked and measured Thermal pressure `Nominal` after the test.

Derived ratios from those exact JSON values:

  iPad / M1 wall throughput, rAF     = 0.4168602643 (41.6860%)
  iPad / M1 wall throughput, timeout = 0.9491908586 (94.9191%)
  iPad / M1 CPU issue, timeout       = 0.9106330187 (91.0633%)

  iPad timeout / iPad rAF throughput = 9.4267233713x

The M1 rAF average contains two startup/outlier intervals (130-140 ms and
430-440 ms); its median and 147/149 normal intervals are 10-20 ms. The iPad
distribution is broadly spread from below 10 ms through 140-150 ms, with a
49.3-ms median. Therefore the medians, complete histograms and query counts are
retained in `presentation-scheduler-split-results.json` instead of presenting
only averages.


Runtime integrity witnesses
---------------------------

  private-event fallback calls = 0
  sampled selector 0x18->0x14 successes = 8
  translated-selector failures = 0
  command-error observer entries = 0

The post-test power sample was:

  Current pressure level: Nominal
  GPU active frequency: 396 MHz
  GPU active residency: 37.73%
  GPU Power: 106 mW

This is a bounded regression, not a long thermal soak.


Conclusion supported by the data
--------------------------------

The iPad native-AGX command/GPU path reaches 94.9% of the same M1 VS Code's
uncapped producer throughput and completes every GPU query. The remaining
large user-visible gap is introduced only when Chromium must wait for a new
visible-frame/rAF opportunity: iPad rAF throughput is 41.7% of M1 and is 9.43x
slower than its own non-rAF producer.

The next root-cause target is therefore the Chromium compositor / WindowServer
presentation and in-flight scheduling chain. Increasing GPU frequency,
weakening command validation, or replacing the now-real private event cannot
explain or fix a 49.3-ms rAF median when the same commands complete at a
5.3-ms producer cadence and about 0.32-ms GPU median.


Test-control limitation
-----------------------

An unrelated deferred Chrome/LLDB workflow intermittently launched suspended
Chrome processes on the iPad. It did not run during these four completed JSON
measurements; the invocation/process audit was checked before and after them.
It did reappear after the GUI was stopped, so a Chromium trace is intentionally
deferred until that external debug workflow exits. No trace or soak result is
claimed here.
