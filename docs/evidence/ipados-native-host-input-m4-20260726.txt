MacWSHost M4 target-process input and visible Terminal evidence -- 2026-07-26
============================================================================

Scope
-----

This record covers the first visible AppKit-control state change caused by the
iPadOS host input path, the RE-backed Terminal startup-window fix, and a
WindowServer crash found while testing non-demo applications.  It does not
claim keyboard/scroll support, independent per-window iPad scenes, or that
Activity Monitor/Finder startup is complete.

1. Why global/per-PID CGEvent posting was insufficient
-------------------------------------------------------

The macOS-side receiver reported the following permission result at runtime:

    MACWS-INPUT READY socket=/private/tmp/macws_host_input.sock abi=3 record=52 display=1 bounds=(0,0 1194x834) pixels=1194x834 postAccess=NO

Both `CGEventPost(kCGHIDEventTap)` and `CGEventPostToPid()` returned after a
down/up pair, but frozen before/after frames showed no change in the intended
GlassDemo checkbox.  Adding PostEvent and Accessibility entitlement strings
did not change `CGPreflightPostEventAccess=NO`; those experimental entitlement
edits were removed.

Runtime-confirmed conclusion: the old `CGEventCreate` +
`CGEventGetLocation` witness observed cursor state visible to the posting
process.  It did not prove that an event entered the target AppKit queue.  The
M2 evidence file contains an explicit correction rather than silently
rewriting the old record.

2. ABI v3 and the target-process AppKit route
---------------------------------------------

Input ABI v3 is a packed 52-byte record.  It retains the physical framebuffer
coordinates/dimensions from v2 and appends the exact `targetPID` returned by
the fixed-operation host service.  Every supported AppKit process already
loads libmachook and owns:

    /private/tmp/macws_app_input.<pid>.sock

`macwsinputd` validates the record and sends it to that socket before trying a
CGEvent fallback.  Inside the exact target process, libmachook maps the
2388x1668 top-left producer coordinate into the 1194x834 bottom-left AppKit
screen coordinate, resolves the containing ordered window, creates an
`NSEvent`, and calls `-[NSApplication postEvent:atStart:]`.

The first implementation used `dispatch_async` to the main queue.  Runtime
logged `APP-INPUT RX` but never `APP-INPUT MAIN`.  The working implementation
uses `CFRunLoopPerformBlock(CFRunLoopGetMain(), kCFRunLoopCommonModes, ...)`
and wakes that run loop.  Verbatim working-process lines are:

    #### APP-INPUT READY pid=39959 socket=/private/tmp/macws_app_input.39959.sock abi=3 record=52
    #### APP-INPUT RX pid=39959 bytes=52 kind=1 target=39959
    #### APP-INPUT MAIN pid=39959 kind=1 target=39959 thread-main=YES
    #### APP-INPUT POST pid=39959 kind=1 window=4 screen=(320.00,482.50) local=(223.00,422.50)
    #### APP-INPUT RX pid=39959 bytes=52 kind=3 target=39959
    #### APP-INPUT MAIN pid=39959 kind=3 target=39959 thread-main=YES
    #### APP-INPUT POST pid=39959 kind=3 window=4 screen=(320.00,482.50) local=(223.00,422.50)

In the corresponding receiver run, the route witness was:

    MACWS-INPUT ROUTE seq=1 route=appkit-socket pid=37808 window=0

The PID differs because that line and the AppKit excerpt above came from two
bounded restarts of the same build.  In each run the record PID and per-app
socket PID were exact matches; mismatched PIDs are rejected by the target.

3. Project LLDB identified GlassDemo's consumed first click
------------------------------------------------------------

The project helper was used as:

    bash misc/ios_lldb_tmux.sh attach 192.168.1.5 22 GlassDemo

Runtime-confirmed via the attached process's `thread backtrace all`: the main
thread was not in the ordinary application loop.  Key frames were:

    -[NSApplication(NSEvent) _nextEventMatching...]
    _NSHLTBMenuEventProc
    TrackMenuCommon
    -[NSMenu popUpMenuPositioningItem:atLocation:inView:appearance:]
    GlassDemo __45-[AppDelegate applicationDidFinishLaunching:]_block_invoke + 180

GlassDemo itself logs:

    [GlassDemo] programmatically popping context menu at vfx center

Therefore the first left click dismisses the demo's startup diagnostic menu;
it does not reach the checkbox.  The host now explains that behavior after
launch.  It does not inject a hidden click or bypass the menu code.

4. Visible checkbox witness
----------------------------

After dismissing that menu, a second down/up pair at physical framebuffer
point approximately `(640,703)` toggled the checkbox.  Direct BGRA comparison
of the two 2388x1668 shared-frame files produced:

The after image visibly contains the check mark.  This is the stability/input

5. WindowServer observer crash while opening Terminal
------------------------------------------------------

The first non-demo run crashed WindowServer in diagnostic logging, not in
Terminal rendering.  Runtime-confirmed via
`WindowServer-2026-07-26-161536.ips`, faulting thread 16:

    objc_msgSend + 32
    _CFErrorFormatDebugDescriptionAux + 164
    _CFErrorCreateDebugDescription + 88
    -[NSError description] + 16
    __macws_vnc_finish_update_block_invoke at Metal_hooks.x:903 + 556

The exception was `EXC_BAD_ACCESS / KERN_INVALID_ADDRESS at 0x10`.  Line 903
was only converting the private/simulator command-buffer error object's
`description` to UTF-8 for a log line.  The fix logs the opaque error pointer
and status without traversing that damaged private object graph.  Retest kept
the same WindowServer alive and safely printed, for example:

    #### VNC-ENDUPDATE-POLL #1 context=0x12172b3a0 tex=0x12178f450 pf=550 cb=0x12178fc90 status=5 polls=0 error=0x121744e00

Crash-report SHA-256:

    df13bb9450bf76e3c3cf35d7a8cfc2318448246c2d957f23756ff13ccb3ae1a6

6. RE-confirmed Terminal startup action
---------------------------------------

Direct execution reached `TTApplication` but produced no visible window.
Launching through chroot `/usr/bin/open -na` failed with
`kLSNoExecutableErr Code=-10827`, so LaunchServices could not provide the
normal open-application path.

`xcrun dyld_info -arch arm64e -objc` on the actual macOS 13.4 Terminal binary
identified:

    0x10000A12C  -[TTApplication applicationShouldOpenUntitledFile:]
    0x10006E6DC  -[TTApplication newShell:]

RE-confirmed via `otool -arch arm64e -tvV`: the first method ends with:

    000000010000a138  mov w2, #0x1
    000000010000a13c  bl  0x1000949a0
    000000010000a140  mov w0, #0x0
    000000010000a144  ldp x29, x30, [sp], #0x10
    000000010000a148  retab

It deliberately returns `NO`; waiting longer cannot create an untitled
window.  Instead of guessing responder selectors, the post-launch hook calls
the real application action.  Runtime-confirmed:

    #### Terminal direct newShell: request
    #### NSApp=0x155910d60 class=TTApplication responds(newShell:)=1
    #### Terminal newShell: returned windows=3

The same WindowServer then acknowledged a capture containing a visible bash
window:

    CAPTURE_ACK:48519:1785055673333926000:7

7. Remaining boundaries
-----------------------

- A specific synthetic click on Terminal's yellow titlebar control did not
  produce a pixel difference, so this record does not claim that action.
  GlassDemo's checkbox is the decisive input witness.
- Keyboard, modifiers, right-click, scroll, Pencil semantics, drag-result
  evidence, and text focus are not implemented yet.
- Activity Monitor and Finder have per-process input endpoints, but their
  direct-launch window behavior has not yet received the same RE/runtime proof
  as Terminal.
- M4 still mirrors the complete macOS display into one iPadOS scene.  It is
  not the final per-CGSWindow architecture.
