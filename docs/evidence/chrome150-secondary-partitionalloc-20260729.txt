Chrome 150 secondary PartitionAlloc address-space failure and port
=================================================================

Date: 2026-07-29
Device: iPad13,6, iPadOS 16.3
Chrome: official Google Chrome 150.0.7871.187, arm64
Scope: current stable Chrome only; no older-browser fallback

The local official application bundle reports 150.0.7871.187.  Google's
Version History API also listed this exact macOS stable release at rollout
fraction 0.99 on 2026-07-29 (serving start 2026-07-27T20:42:10.823633Z).
This is therefore a current-version test, not a compatibility result obtained
by pinning an obsolete browser.

Runtime failure after the primary allocator fix
-----------------------------------------------

The primary Chrome Framework geometry port let Chrome complete application
initialization, enter AppKit's event loop, and begin background work.  A fresh
normal launch then crashed in a separately loaded library:

  report: Google Chrome-2026-07-29-015329.ips
  capture time: 2026-07-29 01:53:10.5615 +0800
  process: Google Chrome, pid 96657
  exception: EXC_BREAKPOINT / SIGTRAP
  faulting thread: ThreadPoolBackgroundWorker
  library: liboptimization_guide_internal.dylib
  library UUID: 4c4c448b-5555-3144-a117-5b3d8107eb3c
  library image offset: 0x00b4a7a8
  ESR: (Breakpoint) brk 0
  x2: 12 (ENOMEM)

The report's VM summary measured `Memory Tag 253` at 24.0 GiB before this
secondary initialization failed.  The loaded main Framework UUID was
4c4c4442-5555-3144-a16b-cc66de5d6913, proving this is the same exact Chrome
150 build as the primary port and not an older-browser result.

RE-confirmed failure path and source contract
---------------------------------------------

Disassembly of the exact optimization-guide dylib maps +0xb4a7a8 to the real
PartitionAlloc HandlePoolAllocFailure path.  Its PartitionAddressSpace copy
still requested a 32-GiB glued mapping for two 16-GiB core pools, followed by
a 16-GiB external metadata region.  The earlier 8-GiB-core diagnostic still
required a 16-GiB glued mapping and failed after the already-live primary
allocator had reserved 24 GiB.

Chromium's branch-heads/7871 `partition_address_space.cc` confirms the
invariant: the glued allocation is `2 * CorePoolSize()`, the BRP pool begins
one core-pool size after the regular pool, and the external metadata region
is at least one core-pool size.  Chromium's own iOS test process uses a
256-MiB core pool.  The selected secondary geometry is a 1-GiB core: four
times that iOS test size while adding only a 2-GiB glued mapping and a 1-GiB
metadata mapping beside Chrome's primary allocator.

Invariant-preserving binary transformation
------------------------------------------

`misc/patch_chrome150_optimization_pa_ios_va.py` is locked to the library
UUID above and makes the following coherent transformation:

  core pool:           16 GiB -> 1 GiB
  glued allocation:    32 GiB -> 2 GiB
  glued alignment:     32 GiB -> 2 GiB
  external metadata:   16 GiB -> 1 GiB
  core base mask:      0xfffffffc00000000 -> 0xffffffffc0000000
  core offset mask:    0x00000003ffffffff -> 0x000000003fffffff
  glued base mask:     0xfffffff800000000 -> 0xffffffff80000000
  glued offset mask:   0x00000007ffffffff -> 0x000000007fffffff

It also locks five MOV/ORR reservation-offset mask materializations, two root
base-mask materializations, and the negative-core arithmetic in
InitMetadataRegionAndOffsets().  All unrelated equal constants remain
unchanged.  The transformation changes 1,318 instructions and refuses an
input with a different UUID, instruction form, count, fixed value, or data
layout.  It does not NOP or redirect HandlePoolAllocFailure.

Runtime validation: passed on current Chrome 150
------------------------------------------------

The signed secondary port was tested in a clean experimental coexistence
session on 2026-07-29.  WindowServer remained the same PID 99972 for the whole
Chrome test; Chrome remained PID 2383 after the final input-bridge restart.
There was no new Chrome crash report (the newest remained the pre-fix 01:55
debugger artifact).  This is a bounded validation, not a long soak.

Exact-browser witness:

  CDP Browser: Chrome/150.0.7871.187
  V8-Version: 15.0.245.21
  WebKit revision: 30f6543ae91e6a860e73b76e3216b663b050f4e5

VNC produced a full 2388x1668 Retina frame containing Chrome's real new-tab
window.  It was neither a black frame nor a stretched low-resolution surface:

  initial frame SHA-256:
    3a6e166220ec09f76de69433847c44f7f840b09fe9dabfc3b72e3edb819a1bc3

The first 12-second WebGL2 control visibly placed its blue 512x512 Metal canvas
in that same VNC frame (SHA-256
f4fb7a83294da0a2a083cf3ddd33a94b0443c3edb14cf9351636f4be6fd098e0) and
returned:

  WebGL version: WebGL 2.0 (OpenGL ES 3.0 Chromium)
  batches / draws: 205 / 20,500
  EXT_disjoint_timer_query_webgl2: supported
  GPU queries: 205 completed, 0 pending
  GPU time: p50 0.860583 ms, p95 0.873125 ms

After the Chrome input fix was rebuilt and loaded, a second 8-second WebGL2
control in the same final Chrome process returned 115/115 completed GPU timer
queries, zero pending, and the same WebGL2 identity.  The corresponding log
window contained validated subtype-1 command translations and eight real
macOS selector 0x18 -> iOS selector 0x14 event translations.  It contained no
IOGPU-ERROR-GETTER, failed MTLCommandBuffer, ProtectionViolation, or command
error.  Earlier Chrome startup work in the same log did contain six
`Internal Error (0000000a)` command-buffer failures, so the session is not
being represented as globally error-free.

The log also contains repeated untranslated selector 0x19 calls returning
0xe00002c2 during the timer-query workload.  All 115 GPU queries nevertheless
completed.  The meaning of selector 0x19 remains unproven and is a separate RE
item; no success claim depends on treating those returns as harmless.

VNC input was first disproved and then fixed with a controlled A/B.  Before the
change, `AppInputBridge.m` excluded Google Chrome, macwsinputd logged
`TARGET-LIST ... result=NULL`, fell back globally despite `postAccess=NO`, and
the DOM remained at clicks=0/text empty.  The fix registers an endpoint only
for the `Google Chrome` main process (not its renderer/GPU helpers) and restores
the public AppKit focus actions a real click establishes before sending the
ordinary NSEvent pair.  The controlled page then visibly showed `CLICKED 1`
and `vncinput150187`; the CDP observer, which did not synthesize input, returned:

  clicks: 1
  text: vncinput150187
  active element: field
  success: true

macwsinputd independently recorded Retina RFB coordinates (724,900) and
(1064,1270), routed both to Chrome PID 2383 via `appkit-socket`, and Chrome
logged main-thread `HIT` / `TAP-COMPLETE` events on
RenderWidgetHostViewCocoa.  The final input frame SHA-256 was:

  b262734270607ccd760246fcc7964330f178cdd19dd7f35659eb08fc0b2ba49b

The exact structured outcomes are retained in
`chrome150-current-stable-vnc-webgl-input-20260729.json`.  This result still
uses the repository's explicitly labelled experimental WindowServer command
and cancelled-swap completion scaffolds; it does not promote those diagnostics
to production protocol fixes.
