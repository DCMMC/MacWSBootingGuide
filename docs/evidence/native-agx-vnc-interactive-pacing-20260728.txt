Native AGX VNC interaction/pacing hardening — 2026-07-28
================================================================

Scope and classification
------------------------

This run used only the native AGX device reported by GlassDemo and the
WindowServer-owned Retina VNC publication path.  It did not enable MTLSim.
The coexistence command/cancel completion adapter and owned BGRA scanout remain
explicit DIAGNOSTIC-SCAFFOLD code.  The changes below improve its correctness
and usability; they are not presented as a production display-completion
protocol.

The final user-facing start command tested in this run was exactly:

    sudo bash /var/jb/usr/macOS/bin/macos_gui.sh start coexist --experimental

The no-watchdog variant was used only while collecting longer debug evidence.
`--experimental` now creates its owned-scanout sentinel itself and defaults to
a 100000-us idle completion interval.  Recent VNC activity selects 16667 us
for one second.  No hidden `touch /tmp/macws_owned_scanout` step or explicit
`--pace-us` argument is needed.

1. Why the live VNC path was slow even after pixels became correct
------------------------------------------------------------------

Before this change the WindowServer publisher copied the complete 15.2-MiB
2388x1668 BGRA frame and advanced its shared sequence on every synthetic
completion, even when every visible byte was identical.  The OSXvnc watcher
therefore woke and compared the same full image hundreds of times.  Runtime
evidence from the old path reached generation 600 with `changed=NO`.

`macws_vnc_mmap_publish_bgra_if_changed` now compares the process-owned linear
source against the stable shared pixels before making the seqlock odd.  An
identical frame does not copy, does not advance the sequence, and cannot wake
the RFB damage path.  A static Terminal A/B emitted this verbatim checkpoint:

    #### VNC-MMAP unchanged skip #600 sequence=48 2388x1668

Thus at least 600 same-pixel producer completions were suppressed while the
published sequence remained 48.  Changed frames retain the existing
odd/copy/even coherent publication.

This removed the previous multi-megabyte no-op RFB churn.  It did not remove
WindowServer's compositor work: a later two-app sample still showed
WindowServer at roughly 40-52% of one CPU and 350-430 MiB RSS.  Those samples
are a remaining thermal/resource limitation, not a stability success claim.

2. Idle versus interactive pacing
----------------------------------

A fixed 100000-us interval reduced idle work but imposed roughly one interval
of latency on each event.  A fixed 16667-us interval was responsive but kept
the diagnostic compositor hot.  OSXvnc now writes a boot-monotonic timestamp
to `/tmp/macws_vnc_activity` at most 120 times per second; WindowServer reads
that timestamp only at its existing SwapEnd scaffold boundary.  It changes no
command bytes and acknowledges no work early.

The exact runtime transition was:

    #### COEXIST DIAGNOSTIC activity pace: mode=interactive pace=16667 us idle=100000 us window=1000ms
    #### COEXIST DIAGNOSTIC activity pace: mode=idle pace=100000 us idle=100000 us window=1000ms

With a real keyboard burst, the retained RFB test first received changed
pixels in 0.411 s.  A changed title drag received its first tile in 0.450 s.
These are end-to-end framebuffer latencies, not handler runtimes.

3. One owner per pointer gesture
--------------------------------

Runtime LLDB evidence had already established two different requirements:

* OSXvnc's original `CGPostMouseEvent` path enters NSWindow's modal move
  tracker and moves a real title bar.
* Delivering that native down together with the AppInputBridge down creates a
  nested mouseDown; AppKit reaches its exact `Periodic events are already
  being generated` branch.

This run added a third concrete witness.  A VNC event at RFB `(512,562)` was
correctly divided by Retina scale 2 and logged as Quartz `(256,281)`, but the
point was not the checkbox (the earlier visual estimate had been made from a
scaled preview).  The AppKit hit-test correctly reported `VFXBox`.  At the
actual physical checkbox coordinate `(650,714)`, target resolution and hit
testing produced:

    #### OSXVNC INPUT kind=6 gesture=3 point=(650.0,714.0)/2388x1668 sent=52 errno=0 attempts=1 reliable=YES
    #### OSXVNC CLICK-OWNER route=app-input gesture=3 point=(650.0,714.0) sent=YES
    MACWS-INPUT TARGET-PROBE nonce=3 endpoints=2 sent=2 replies=2 selected=61045 window=11 score=3 ambiguous=NO
    MACWS-INPUT ROUTE seq=3 route=appkit-socket pid=61045 window=11
    #### APP-INPUT HIT pid=61045 gesture=3 kind=6 window=11 screen=(325.00,477.00) local=(228.00,417.00) content=(228.00,417.00) view=NSButton
    #### APP-INPUT TAP-COMPLETE pid=61045 gesture=3 window=11 screen=(325.00,477.00) local=(228.00,417.00)
    #### APP-INPUT CONTROL-RESULT pid=61045 gesture=3 phase=tap view=NSButton enabled=YES has-value=YES before=0.000000 after=1.000000

The final retained screenshot visibly contained the blue check mark.

The VNC mouse hook now buffers a possible left down for a 3-logical-point
slop radius.  A stationary release sends one atomic AppInput tap to the
uniquely selected AppKit process.  Crossing the slop radius replays the down
and subsequent drag through OSXvnc's original native path.  The corresponding
drag proof was:

    #### OSXVNC DRAG-OWNER route=native gesture=4 point=(1360.0,260.0)
    INPUT PASS operation=title-drag latency=0.450s updates=1 raw_rectangles=1 raw_pixels=16384

The retained 2388x1668 frame visibly showed GlassDemo moved down and right,
with Terminal exposed behind it.  This is routing by gesture semantics, not a
constant-return hook or event-permission bypass.

4. Terminal key delivery versus final-frame publication
--------------------------------------------------------

The key path had two independent delays.  The first is Terminal's AppKit
redraw race.  The Terminal-only launch environment installs a debounced
750-ms responder invalidation; it is not installed in other applications.
LLDB caught Terminal's natural delayed invalidation at:

    frame #0 AppKit`-[NSView setNeedsDisplayInRect:]
    frame #1 Terminal`___lldb_unnamed_symbol912 + 840
    frame #2 Foundation`__NSFireDelayedPerform + 372

The second delay was found by keeping the same RFB connection after a fast
command.  All 36 down/up events for `echo settledproof` reached Terminal, and
the final key-up was observed at monotonic 221832.638473.  Terminal's display
settle ran at 221833.436075:

    #### APP-INPUT DISPLAY-SETTLE pid=63084 serial=18 window=4 responder=NSKVONotifying_TTView string-length=179168 forced=YES needed-before=NO needed-after=NO delay=750ms elapsed=19.352ms at=221833.436075

The old VNC final request occurred only 350 ms after the last key-down, before
that boundary.  In the failing A/B the complete command and output appeared
only after the next keyboard interaction requested another compositor frame.
This rules out lost keyboard events: the target AppKit log contained every
event, while publication was one transaction behind.

OSXvnc now retains its early progress/final requests and adds one debounced
1100-ms `KEY-SETTLED` capture.  The passing trace was:

    #### OSXVNC KEY-FINAL-CAPTURE serial=18 detail=0xff0d generation=1785184363229981000
    #### OSXVNC KEY-SETTLED-CAPTURE serial=18 detail=0xff0d generation=1785184363986376000
    #### VNC-FINAL acknowledged pid=62833 generation=1785184363986376000

On one retained connection, a 10-ms-per-character burst completed with:

    INPUT PASS operation=keyboard latency=0.274s updates=1 raw_rectangles=1 raw_pixels=4096
    SETTLE retained=3.000s updates=6 changed_updates=4 final_digest=2d5fc66d5424200bea6a198a362e73a3b5f28325a72a47867004ec1c07f877ae

The final screenshot visibly contained all three lines without another input:

    bash-3.2# echo settledproof
    settledproof
    bash-3.2#

6. One-command lifecycle and remaining limits
----------------------------------------------

Immediately before the final one-command start, `macos_gui.sh stop` reported
both owned scanout and pace sentinels absent.  Starting with only
`start coexist --experimental --no-watchdog` then logged:

    [macos_gui] DIAGNOSTIC-SCAFFOLD: command ABI + cancelled-swap completion + read-only PF550 completion observer + bounded submit flight recorder + owned BGRA scanout + stable VNC mmap enabled.
    [macos_gui] DIAGNOSTIC-SCAFFOLD: synthetic completion pace=100000 us (not a refresh-rate implementation).
    [macos_gui] WindowServer graphics ready (pid=61829, clean producer observed).
    [macos_gui] VNC: Retina first frame ready (WindowServer pid=61829, generation=1785184091).

The sentinels then contained:

    owned=present
    pace=100000

The normal command keeps the 300-second diagnostic watchdog.  The owned
scanout cache and cancelled-swap completion still need a substantially longer
thermal/resource soak before either can lose its diagnostic label.  In
particular, unchanged-frame suppression reduces memory/RFB traffic but cannot
be used as evidence that native WindowServer render CPU is solved.

The final `macos_gui.sh stop` restored iOS.  A two-second delayed process
query returned no WindowServer, OSXvnc-server, Terminal, GlassDemo, or
macwsinputd line, and the remaining state check was:

    owned=absent
    pace=absent
    04:35:21  up 2 days 13:39,  1 user,  load average: 2.13, 2.89, 2.97
