Chrome 150 PartitionAlloc address-space failure on iPad13,6
============================================================

Date: 2026-07-28
Device: iPad13,6, iPadOS 16.3
Chrome: Google Chrome 150.0.7871.187, arm64
Chrome Framework UUID: matched the loaded image and crash report
Scope: diagnostic evidence only; no invariant was bypassed

Observed failure
----------------

The first official arm64 Chrome launch did not reach ANGLE or Metal. It
terminated during Chrome Framework static initialization:

  crash report: Google Chrome-2026-07-28-111937.ips
  exception: EXC_BREAKPOINT / SIGTRAP
  Chrome Framework file offset: 0x77703e0

Runtime LLDB backtrace (framework-relative addresses):

  0x077703e0
  0x0128b620
  0x0128ab1c
  0x0128a9ec
  0x0128a820
  0x0128a470
  dyld initializers

The call chain is Chrome's PartitionAddressSpace initialization. The trap
function at 0x77703a0 calls the page-allocation error accessor and executes a
BRK. At the trap, LLDB measured x2 = 0xc, which is errno 12 (ENOMEM).

Relevant Chrome Framework disassembly
-------------------------------------

The following is the relevant logic around framework offset 0x128b4fc. The
two 0x800000000 operands are the 32-GiB size and alignment of the glued pair
of 16-GiB macOS core pools:

  mov  x0, #0
  mov  x1, #0x800000000
  mov  x2, #0x800000000
  ...
  bl   0x13ba4f0
  ...
  cbz  x0, 0x128b61c
  ...
  0x128b61c: bl 0x77703a0

This is RE-confirmed from the exact Chrome Framework binary that generated
the crash. The source-equivalent logic is also present in Chromium tag
150.0.7871.187:

  base/allocator/partition_allocator/src/partition_alloc/
      partition_address_space.cc
  base/allocator/partition_allocator/src/partition_alloc/
      partition_alloc_constants.h

For macOS, kPoolMaxSize is 16 GiB and initialization reserves two glued pools
as one 32-GiB allocation aligned to 32 GiB. The iOS branch instead uses an
8-GiB maximum and supports a dynamically smaller regular pool.

LLDB observation at the exact mmap call
---------------------------------------

An LLDB breakpoint on mmap with condition `$x1 >= 0x400000000` captured the
first large reservation:

  hint   = 0x11800000000 (one run; another used 0x10000000000)
  length = 0x800000000
  prot   = 0
  flags  = 0x1002 (MAP_PRIVATE | MAP_ANON)
  fd/tag = 0xfd000000
  return = 0x280000000

The kernel ignored the high hint and returned a valid but only 2-GiB-aligned
32-GiB range. Chrome therefore unmapped it. Its fallback over-allocation of
almost 64 GiB then failed with ENOMEM and reached the BRK above.

As a diagnostic only, LLDB changed the flags at this call to include
MAP_FIXED. Exact bases 0x800000000, 0x1000000000, and 0x2000000000 all
returned MAP_FAILED. No binary patch or permanent behavior change was made.

Cross-context virtual-address probe
-----------------------------------

`misc/va_alignment_probe.c` was compiled twice from the same source: once as
an iOS-native process and once as a macOS arm64 process run in the chroot.
Both produced the same allocation results:

  page_size=16384 task=0x203
  mach_vm_map size=32GiB align=32GiB -> kr=0x3 ((os/kern) no space available) address=0x0 aligned=no
  mach_vm_map size=16GiB align=16GiB -> kr=0x0 ((os/kern) successful) address=0x400000000 aligned=yes
  mach_vm_map size=8GiB align=8GiB -> kr=0x0 ((os/kern) successful) address=0x400000000 aligned=yes
  sequence16[0] -> kr=0x0 address=0x400000000
  sequence16[1] -> kr=0x0 address=0x800000000
  sequence16[2] -> kr=0x3 address=0x0
  sequence16 adjacent01=yes adjacent12=no pair32aligned01=no pair32aligned12=yes
  mmap hint=0x10000000000 size=32GiB -> 0x280000000 errno=0 (Undefined error: 0) aligned=no
  mmap hint=0x0 size=32GiB -> 0x280000000 errno=0 (Undefined error: 0) aligned=no

Runtime-confirmed conclusions
-----------------------------

1. The failure precedes ANGLE, WebGL, Metal device creation, and AGX command
   submission. It cannot yet be attributed to the native GPU bridge.
2. The same limitation in an iOS-native executable rules out chroot-specific
   syscall translation and a missing macOS-binary entitlement as the cause.
3. The device can reserve two adjacent 16-GiB aligned entries at 16--32 GiB
   and 32--48 GiB, but that pair starts at 16 GiB and therefore violates the
   32-GiB base-alignment invariant encoded by Chrome's macOS PartitionAlloc.
4. Merely accepting the unaligned mapping would be wrong: pool membership and
   base calculations inline the 16-GiB/32-GiB masks throughout the framework.

Binary scan and implementation consequence
------------------------------------------

A Capstone operand scan of the exact thinned arm64 Chrome Framework found:

  immediate -0x400000000: 7060 instructions
  immediate  0x800000000: 181 instructions

Not every match belongs to PartitionAlloc, but the density proves that a
local two-instruction size patch cannot preserve the allocator invariant.
Replacing the constants globally would also alter unrelated code and is not
a viable fix.

Next test paths
---------------

* Preferred: test an official native-arm64 Chromium build predating macOS
  PartitionAlloc-Everywhere, while retaining ANGLE's Metal backend. This
  avoids modifying allocator invariants and can expose the actual AGX/WebGL
  behavior.
* Diagnostic only: make Chrome's allocator bootstrap observe an already
  registered PartitionAlloc-named malloc zone, solely to discover the next
  failure. This is not a fix unless all allocation/free ownership and direct
  PartitionAlloc users are proved compatible.
* Long term: rebuild Chromium for macOS UI with the iOS-sized PartitionAlloc
  geometry. This preserves semantics but is substantially larger work.
