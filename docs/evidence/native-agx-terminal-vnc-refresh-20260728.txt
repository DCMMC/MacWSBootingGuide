# Native-AGX Terminal PF550 + persistent VNC refresh validation (2026-07-28)

## Scope and result

This milestone addresses the reported state in which Retina VNC showed a
static Terminal, pointer motion was visible, but clicks appeared to do nothing.
It uses OSXvnc only; MacWS Host is outside the pixel and input path.

The final bounded run runtime-confirms all of the following on one persistent
RFB 3.8 connection:

* desktop geometry remained 2388x1668;
* a physical RFB click reached the real Terminal AppKit process;
* Terminal handled the green title-bar control and changed its GPU output;
* the same client received a later full 2388x1668 incremental rectangle;
* its accumulated framebuffer hash changed and the final PNG is a sharp,
  correctly oriented full-screen Terminal, not a recovery colour or stretched
  logical-resolution image;
* the current WindowServer log segment contains no new PageFault or
  `AGX_SUBMIT_ERROR`.

The run ended with `misc/cleanup_all.sh` and iOS was restored.

## 300x210 PF550 resource invariant

The pre-fix first Terminal fault was runtime-confirmed at the resource layer.
The ordinary texture fallback created plain pixel format 550 as a four-byte
linear BGRA IOSurface:

    300x210-pf550-bpe4-fccBGRA map=UNKNOWN-FALLBACK-BGRA4
    IOGPU-CALLBACK-BUFFER ... target=300x210 errorCode=3 ... PageFault

The replacement constructor uses the native two-plane compressed layout:
16x16 tiles, 1024-byte colour-tile data, 256-byte metadata-tile data, a
0x40000-byte header reserve per plane, private fourcc `0x26623338`, and the
same cache/PurpleGfxMem properties observed on native display surfaces. The
post-fix runtime reported:

    #### MTL_TEX PF550-SURFACE: 300x210 ... actualAlloc=0xd3200 rawCompressionType=0 rawHeightInTiles=0 compatibleCompressionType=3 compatibleHeightInTiles=14
    #### MTL_TEX POOL-NEW: key=300x210-pf550-bpe2-fcc643969848 ... map=PF550-COMPRESSED

This is not a validator bypass. The raw IOSurface getters remain zero on this
iOS, while the existing compatibility layer returns the descriptor values
actually consumed by AGX.

A one-shot delayed GPU read proved that exact small texture contained the
complete Terminal rather than merely avoiding a crash:

    #### PF550-SMALL-PROBE result ... executed=YES readable=YES bpr=1280 rgb=15006/15750 different=15688 first=0 pipelineError=nil

Its PNG hash is:

    d5c5041811982193994603f5764c9754ea81bd10991643473dff9c6185b0e8f9  probe-300x210.png

The binding diagnostic independently captured the same 300x210 PF550 texture
at fragment slot 3 while rendering a 2388x1668 PF550 target, and the associated
command buffers completed `status=4 error=0`. Thus both application rendering
and downstream compositor consumption are runtime-confirmed.

In the final run, the current session starts at the last

## Window geometry and first-frame classifier

The GPU readback first exposed only a menu bar and a title-bar sliver. Runtime
AppKit geometry identified the upstream cause:

    frame=(0.0,-77.0 150.0x105.0)
    visible=(0.0,0.0 1194.0x809.0)
    intersection=4200.0/15750.0

The Terminal startup path now preserves a valid saved position, but clamps a
window whose visible intersection is below 50% fully into `visibleFrame`. The
next run reported:

    #### Terminal geometry: repositioned ... origin=(0.0,-77.0)->(0.0,0.0)
    #### Terminal geometry: ... intersection=4200.0/15750.0 moved=YES

The exact before/after rejected-frame witnesses are:

    68d23bab02e5b2eb8b5e9b938af6486dd6295982ac831425b67c53059f481b0d  title-only/offscreen PNG
    88ef14b097fe8e4ed4dda2533df848ff38e0b121ad7229fd400b19b5d4bc7ba9  clamped/full-window PNG

The old 5% area threshold could not admit a legitimate 300x210 Retina window.
The spatial classifier samples at 16-pixel intervals, requires diversity, and
requires at least six non-menu rows containing four RGB samples. The offscreen
frame measured 231 RGB samples across 4 dense rows; the complete clamped frame
measured 392 RGB samples across 13 dense rows. This classifier is applied to
all normal mmap publication paths; it does not force an invalid frame through.

## RE-confirmed live-update root cause

SHA-256 of the exact universal OSXvnc binary copied from the device:

    c19a08dee9d60c73d05751f0ed3fca1b92bf162e96fca38f6af10d2fa69c2ac6  OSXvnc-server

The running process uses its arm64 slice. `otool -arch arm64 -tvV` and the
binary's symbol table establish these exact offsets:

* `_refreshCallback` at image `+0xd114` locks each client at `+0x88`, unions a
  CGRect into `client+0xf8` at `+0xd200` (`refreshCallback+0xec`), unlocks,
  then signals `client+0xc8` at `+0xd210`.
* `_clientOutput` at image `+0xd3ac` intersects `modifiedRegion(+0xf8)` with
  `requestedRegion(+0x108)` at `+0xd4c8`, subtracts the sent region at
  `+0xd4d8`, and calls `_rfbSendFramebufferUpdate` at `+0xd500`.
* an RFB FramebufferUpdateRequest unions its rectangle into
  `requestedRegion(+0x108)` at `+0x14974`; only a non-incremental request also
  unions it into `modifiedRegion(+0xf8)` at `+0x1498c`.

Therefore a fresh client/full request could read the latest mmap while an
already-connected incremental client only received CoreGraphics' small
cursor/window rectangles. This exactly explains the misleading combination
"reconnect works, live view is frozen".

Before the generation fix, one persistent RFB client received only these raw
rectangles after the click:

    (0,0 13x19)
    (104,829 17x5)

The test initially rendered those rectangles on a zeroed temporary buffer and
looked black; that display was correctly rejected as a client-test bug. When
applied to the retained framebuffer, they merely patch tiny areas and leave
the old desktop almost entirely unchanged.

## Shared mmap publication protocol and final same-connection witness

The mmap remains `16-byte header + BGRA pixels`, with an aligned atomic
uint64_t sequence appended after the pixels. A WindowServer writer serializes
validated publishers, stores an odd sequence, copies the complete frame, then
release-commits the next even sequence. OSXvnc acquire-loads the sequence
around every read and retries if it changed. Its watcher invokes the original
RE-confirmed `_refreshCallback` with one 2388x1668 CGRect only after observing
a new even sequence. This uses OSXvnc's own region locking and wakeup protocol;
it does not mutate client structures directly.

The final persistent test used the repository's `misc/vnc_live_click.py`
protocol: initial full request, outstanding incremental request, RFB pointer
down/up, and cumulative application of every returned rectangle. Runtime logs
show the complete input path:

## Remaining boundary

The click/refresh freeze reported for Terminal is fixed in this bounded run.
This does not close the existing Terminal close-cleanup lock, keyboard/scroll
support, the diagnostic KCMD/cancelled-swap scaffolds, or long-soak thermal
stability. Those remain separate milestones.
