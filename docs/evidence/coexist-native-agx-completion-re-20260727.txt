MacWSBootingGuide native-AGX completion / PF550 RE evidence
Date: 2026-07-27 (Asia/Shanghai)
Device: iPad13,6, iOS 16.3, macOS 13.4 chroot

Scope
-----

This evidence pass answered three bounded questions without changing an AGX
descriptor or callback result:

1. What arguments build the 1140x798 pixel-format-550 texture descriptor?
2. Does selector 0x107 or the command completion queue expose the fault VA?
3. Can the libmachook-only deployment loop avoid rebuilding the aggregate
   Theos project?

PF550 producer ABI and actual 1140x798 call
--------------------------------------------

Runtime Objective-C type encodings from the actual process:

  updateBindDataWithAddresses:cpuMetadataAddress:gpuVirtualAddress:
      isCompressible:shouldInitMetadata:
    types=v48@0:8^v16^v24Q32B40B44
  updateBindDataWithAddresses:gpuVirtualAddress:
    types=v32@0:8^v16Q24
  updateBindDataWithAddresses:gpuVirtualAddress:shouldInitMetadata:
    types=v36@0:8^v16Q24B32

The ABI-correct, forwarding-only five-argument observer recorded this exact
call before the first 1140x798 PageFault:

  UPDATEBIND-FIVE role=target-1140 #1 tex=0x136768650 1140x798 pf=550
  surface=145 cpuAddress=0x10817c000 cpuMetadata=0x0
  gpuVA=0x1500070000 compressible=0 initMetadata=0
  callerStatic=0x1e5a5afc8 gpu40=0x1500070000
  address=0x1500070000 raw=0xffff13f7ef400
  layout=0 compressed=0 extended=1 alloc=0x384000
  headerOffset=0 headerSpan=0 beforeFound=0

The correlated raw completion was:

  IOGPU-CALLBACK-BUFFER commandBuffer=0x13676a960
  submitSerial=328 fixed=8 target=1140x798 errorCode=3

and the render-target join reported 11 targets.  The target descriptor did not
exist at method entry and was generated by Apple's original method after the
observer forwarded all arguments unchanged.

Project-LLDB disassembly of the original five-argument method (static
0x1e57716b4) confirms that x19 is the supplied GPU VA and x20 is the supplied
CPU address.  The w5==0 branch skips metadata setup.  The common tail stores
x20 at primary-object +0x130 and x19 at +0x40, then calls the object's
texBaseAddressesUpdated virtual.

Correction from current Mesa Asahi source
-----------------------------------------

Mesa Asahi commit 0d4d1907bd35acfe80208d10deeb0cb134f79c60 was inspected
locally.  src/asahi/genxml/cmdbuf.xml defines texture layout 0 as Linear and
marks the acceleration-buffer field "If layout is compressed".  For linear
textures the overlapping extended bits encode linear depth/layer stride.
src/asahi/vulkan/hk_image_view.c likewise assigns acceleration_buffer only
inside `if (layout->compressed)`.

Therefore `raw & ((1<<36)-1)` from the 1140x798 layout=0/compressed=0
descriptor is not an acceleration GPU VA.  The earlier theory that the
0x13f7ef4000-looking value was an unmapped metadata address is disproved; no
descriptor-field rewrite follows from it.

Selector 0x107 is not the PageFault payload path
------------------------------------------------

The selector registration witness was:

  AGXIOC ASYNC-REGISTER #1 ... sel=0x107->0x107 ... refCnt=3
  AGXIOC ASYNC-REFERENCE ... index=1 value=0x20912da08
    symbol=AGX::Device<...>::deviceNotificationCallback(void*,uint,uint64,uint64)

Project LLDB disassembled the current-process implementation at static
0x1e575da08.  The function:

  * returns when w1 is nonzero;
  * returns when w2 is 1;
  * for w2==0, stores w3/x3 at Device+0x740 and wakes registered listeners;
  * sends every other w2 value through the literal
    "*** Invalid AGX device notification" path.

It does not read a pointed fault structure or a fifth argument.  Selector
0x107 is an AGX device-notification path, not the command-buffer PageFault
payload path.

Command completion record contains status but no fault VA
---------------------------------------------------------

LLDB stopped at the real IOGPU
`-[IOGPUMetalCommandBuffer didCompleteWithStartTime:endTime:error:]` original
IMP for an NSError whose object+0x10 was Code=3.  The stack was:

  frame #0  IOGPU 0x1b39e2be8
  frame #1  Metal 0x1a01093c8
  frame #2  IOGPU 0x1b39e3fa4
  frame #3  IOGPU 0x1b39ec190
  frame #4  IOGPU 0x1b39ec29c

RE of frame #3 (function starts at 0x1b39ec110) shows a repeated 0x20-byte
notification-queue record.  It loads:

  +0x00  callback/command-buffer object
  +0x08  start timestamp
  +0x10  end timestamp
  +0x18  32-bit completion status

then calls the object's virtual callback with x0=object, x1/x2=converted
timestamps, and w3=status.  Frame #2 (function starts at 0x1b39e3f14) receives
exactly those values, creates NSError when w3 is nonzero, and forwards only
the NSError.  No fault address exists in this userspace completion record.

Consequently, waiting for another NSError/userInfo key or wrapping selector
0x107 cannot recover the VA.  The next evidence target is either a fresh
kernel gpuEvent report or indirect GPU addresses stored in the resources
referenced by the faulting KCMD.

Direct KCMD/resource boundary
-----------------------------

The exact PageFault batch retained under /tmp/macws-pf550-target-20260727 has
8 internally valid segments and 45 unique resource gids.  All aligned direct
GPU-VA literals recognized in the 0x41d8-byte KCMD fall inside active resource
ranges.  The lifecycle snapshot reports create_fail=0, destroy_fail=0, and
unmatched_destroy=0 for that boundary.  This rules out a direct literal VA
outside the recorded live ranges; it does not inspect second-level descriptor
addresses stored inside those resources.

Safety / crash-report reset
---------------------------

Before a bounded fresh PageFault attempt, 38 matching WindowServer/GlassDemo
reports were copied to /tmp/macws-crash-archive-20260727-1102 and then removed
from the device CrashReporter directory.  The attempt reproduced Code=3 for
1140x798 and was immediately cleaned up, but emitted no new gpuEvent .ips.
That absence is recorded as a negative result; no fault address is inferred.
