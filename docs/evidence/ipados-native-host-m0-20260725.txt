MacWSHost M0 implementation evidence -- 2026-07-25
====================================================

Scope
-----

This record covers the first iPadOS-native host implementation.  It does not
claim per-macOS-window transport or completed input injection.  The producer
was native-AGX WindowServer; OSXvnc-server was not running.

1. App structure and local build
--------------------------------

The root aggregate now builds MacWSHost.  Its Info.plist contains:

    UIApplicationSceneManifest = {
        UIApplicationSupportsMultipleScenes = true;
        UISceneConfigurations = {
            UIWindowSceneSessionRoleApplication = (... MacWSSceneDelegate ...);
        };
    };

The host-side Theos build completed for arm64:

    ==> Compiling main.m (arm64)...
    ==> Linking application MacWSHost (arm64)...
    ==> Generating debug symbols for MacWSHost...
    ==> Signing MacWSHost...

2. Why the application is arm64-only
------------------------------------

The first on-device fat arm64+arm64e build died before main.  Verbatim excerpt
from `/var/mobile/Library/Logs/CrashReporter/MacWSHost-2026-07-25-210752.ips`:

    "exception" : {"type":"EXC_BREAKPOINT","signal":"SIGTRAP"}
    "esr" : {"description":"(Breakpoint) pointer authentication trap DA"}
    frame 0: readClass(objc_class*, bool, bool) + 112
    x0: OBJC_CLASS_$_MacWSMappedFrame

The arm64-only build passed libobjc initialization on the same iPad13,6.  This
is a build-tool ABI boundary, not justification for a global libobjc PAC
bypass.

3. Dedicated entitlements
-------------------------

Signing the app with the project's WindowServer/backboardd entitlement set
made UIKit abort before the application delegate.  Verbatim excerpt from
`MacWSHost-2026-07-25-210904.ips`:

    EXC_CRASH / SIGABRT, "abort() called"
    +[UIScreen mainScreen] + 408
    -[_UIRemoteKeyboards _activeScreen] + 164
    +[UIKeyboardSceneDelegate automaticKeyboardArbiterClient] + 60
    _UIApplicationMainPreparations + 1296
    UIApplicationMain + 320

With MacWSHost's dedicated minimal entitlement file, the same binary remained
running and connected its scene:

    72682 ... /Applications/MacWSHost.app/MacWSHost

Later persistent app-log witness:

    1784985265.333 launched native-device=(null) frame-path=/var/mnt/rootfs/private/tmp/macws_vnc_fb
    1784985265.347 scene-connected id=F7744CD1-31D6-4C18-BEB8-FA7DCE0FC30D role=UIWindowSceneSessionRoleApplication

This A/B proves that the broad entitlement set as a whole caused the UIKit
failure.  It does not identify one entitlement as the individual cause.

4. No-VNC native-AGX producer witness
-------------------------------------

WindowServer was started with:

    macos_gui.sh start coexist --no-terminal --no-vnc

`macos_gui.sh status` reported `VNC: not running`.  GlassDemo and WindowServer
remained present.  After explicitly arming the existing one-shot PF550 capture,
WindowServer logged:

    #### VNC-FINAL pipeline ... contract=OK error=nil
    #### VNC-FINAL clear-control executed=YES pixel=OK center=804020ff
    #### VNC-FINAL control clear=OK draw=EXECUTED pixel=OK center=214365ff
    #### VNC-FINAL captured 2388x1668 BGRA8 cpu130=0x10c3dc000 base=0x10c3dc000 bpr=9600 sampled_nonzero=2864

The resulting file was:

    -rw-r--r-- 1 root wheel 15932752 ... /var/mnt/rootfs/private/tmp/macws_vnc_fb

Thus the M0 producer can publish nonzero GlassDemo pixels without an RFB
server.  This is still the explicitly gated PF550 diagnostic path, not the
final continuous per-window transport.

5. Current iOS Metal enumeration boundary
------------------------------------------

The first persistent host diagnostic logged:

    launched native-device=(null)

The existing iOS-native mtl_keepalive tool independently printed:

    MTLCreateSystemDefaultDevice returned nil

Stopping WindowServer and restoring SpringBoard/backboardd did not change
either result.  Removing `platform-application` from the host entitlement set
also did not change it.

Remote LLDB used the actual installed binary's bind table (the device build's
MTLCreateSystemDefaultDevice GOT slot was `base+0x10030`) and resolved the
runtime entry to 0x191523584.  The first instructions were:

    0x191523584: pacibsp
    0x191523588: sub sp, sp, #0x80
    ...
    0x191523638: bl 0x19162a648
    0x19152363c: ldr x8, [sp, #0x38]
    0x191523640: ldr x19, [x8, #0x28]
    0x191523650: mov x0, x19

Disassembly of the exact iOS 16.3.1 Metal binary at
`iOS DeviceSupport/iPad13,6 16.3.1 (20D67)/Symbols/.../Metal` confirms that
`MTLRegisterDevices` matches `IOAcceleratorES`, iterates its services, calls
`getMetalPluginClassForService`, constructs each device with
`initWithAcceleratorPort:`, and passes successful objects to `MTLAddDevice`.
The current process's resulting device array is empty.

Correction preserved for future sessions: an intermediate THEORY said the
Metal GOT slot pointed at memset.  That was false because the first LLDB read
used the local-build offset (`+0x100c0`) against a differently laid-out
device-build binary.  `llvm-objdump --macho --bind` proved that the device's
`+0x100c0` slot really was memset and its Metal slot was `+0x10030`.  Reading
the correct slot produced the real Metal function above.

A userspace reboot was then requested to reset process-global Metal/device
registration without a full power cycle.  The continuation below records the
post-reboot result and corrects the earlier incomplete attribution.

6. Root cause and native iPadOS Metal presentation
--------------------------------------------------

After the userspace reboot, both MacWSHost and the independent
`mtl_keepalive` probe still returned nil.  IORegistry nevertheless contained
one live accelerator and all plugin-registration inputs were valid:

    metal-registry service=AGXAcceleratorG13G_B0 plugin=AGXMetal13_3 class=AGXG13GDevice bundle=/System/Library/Extensions/AGXMetal13_3.bundle loaded=YES realized=AGXG13GDevice
    metal-registry enumeration kr=0x0 count=1

The exact iOS 16.3.1 Metal binary provides the RE boundary:

- `_MTLRegisterDevices` at `0x181d2df78` matches `IOAcceleratorES`, calls
  `_getMetalPluginClassForService`, then `initWithAcceleratorPort:` and
  `_MTLAddDevice`;
- `_getMetalPluginClassForService` at `0x181c4d15c` reads
  `MetalPluginName` and `MetalPluginClassName` and loads
  `/System/Library/Extensions/<MetalPluginName>.bundle`;
- `_MTLCreateSystemDefaultDevice` at `0x181c47584` reads the registered device
  array and returns nil when its count is zero.

Live unified logging while launching the unprivileged A/B build identified
the actual failing operation.  Verbatim device excerpts:

    Failed to create an IOAccelDevice... IOServiceOpen returned kIOReturn(0xE00002E2)
    System Policy: MacWSHost(76384) deny(1) iokit-open-user-client AGXDeviceUserClient
    IOUC AGXDeviceUserClient failed MACF in process pid 76384, MacWSHost
    System Policy: MacWSHost(76384) deny(1) iokit-open-user-client IOSurfaceRootUserClient
    IOUC IOSurfaceRootUserClient failed MACF in process pid 76384, MacWSHost

This is runtime confirmation that Metal registration reached the real AGX
service but the process MAC policy denied the two user-client opens.  It is not
an entitlement-string theory and not evidence of a missing driver bundle.

The minimal A/B fix adds exactly those two classes to
`com.apple.security.iokit-user-client-class`; it does not import the broad
WindowServer entitlement set.  The first launch after signing produced:

    1784991369.219 launched native-device=Apple M1 GPU supportsMultiple=YES frame-path=/var/mnt/rootfs/private/tmp/macws_vnc_fb
    1784991369.219 metal-registry service=AGXAcceleratorG13G_B0 plugin=AGXMetal13_3 class=AGXG13GDevice bundle=/System/Library/Extensions/AGXMetal13_3.bundle loaded=YES realized=AGXG13GDevice
    1784991369.219 metal-registry enumeration kr=0x0 count=1
    1784991369.399 scene-connected id=2442C92E-2470-4A05-9EC8-E8D8923C837B role=UIWindowSceneSessionRoleApplication
    1784991369.421 runtime-confirmed source frame nonzero 2388x1668 stride=9552 path=/var/mnt/rootfs/private/tmp/macws_vnc_fb
    1784991369.426 runtime-confirmed native Metal present scene=b1fcb7e3489c9545 frame=2388x1668 status=4 error=nil

`status=4 error=nil` is the completed iOS-native render/present command-buffer
witness.  Process uptime or the UIKit fallback is not counted as success.

Adding `platform-application` on top did not change either Metal success or
the scene-creation result, so it was removed rather than retained as an
unnecessary privilege.

7. Multiple-scene boundary
---------------------------

The application reports `supportsMultipleScenes=YES`, and its first scene is
connected, but every second-scene request is currently rejected by the host:

    scene-activation requested supportsMultiple=YES connected=1 open=1 origin=2442C92E-2470-4A05-9EC8-E8D8923C837B mode=all-nil
    scene-activation failed: Error Domain=FBSWorkspaceErrorDomain Code=2 "the host declined to create a scene" UserInfo={NSUnderlyingError=... Error Domain=SBSceneManagerCoordinatorDomain Code=1 "Scene creation failed" ... BSErrorCodeDescription=Denied}

The same result was reproduced with (a) an NSUserActivity and no options,
(b) an NSUserActivity plus `requestingScene`, (c) a unique
`targetContentIdentifier`, and (d) session/userActivity/options all nil.
`platform-application` was also an unchanged A/B.  Therefore none of those is
promoted as the cause.

RE-confirmed via the exact SpringBoard binary:

- `-[SBSceneManagerCoordinator _createSceneForApplication:withOptions:completion:]`
  starts at `0x1c7abfbb0`;
- its transition block starts at `0x1c7abfdfc`;
- it reads the request `identifier` at `0x1c7abfe84`, follows the iPad stored
  persistence path, calls `_sceneIdentifierForStoredPersistenceIdentifier:`
  at `0x1c7ac01e0`, and constructs domain code 1 at `0x1c7ac026c` when that
  lookup is nil.

Removing `targetContentIdentifier` and then passing all public API parameters
as nil did not avoid the runtime error.  That disproves the first theory that
the app-created target identifier alone selected the failed persistence path.
The next useful witness must inspect the actual request object or the stored
scene mapping at runtime; forcing the branch is not a fix.

The project LLDB runner was tried against SpringBoard, but its remote
`process connect` failed and left SpringBoard traced-stopped.  launchd
restarted it after debugserver was terminated.  No register/object claim from
that failed attempt is used as evidence.

8. Explicit M0/M1 limits
------------------------

- Every scene currently displays the complete 2388x1668 desktop.
- The mmap header has no generation or atomic-publish state.
- Input-v1 records are coordinate-validated/logged only.
- UIKit fallback code remains explicitly labelled for recovery, but the
  current signed device build now takes the real Apple M1 Metal path.
- One scene is runtime-confirmed; the second-scene host-policy failure remains
  open and is independent of native GPU access.
